# Message Central VerifyNow — setup and what changed

Sign-up and sign-in send a 4-digit SMS code through Message Central VerifyNow
(India, +91). Message Central generates, sends and validates the code. Every
call to it is made in Django; the Next.js app only talks to our own API.

Decision record: `docs/DECISIONS.md`, DEC-014. Commit: `3f67d4af`.

## 1. Environment variables

Put these in `backend/.env` (git ignores that file). Never commit real values.

| Variable | Value |
| --- | --- |
| `MC_CUSTOMER_ID` | Your Message Central customer id (looks like `C-XXXXXXXX`) |
| `MC_PASSWORD` | Your Message Central account password, as plain text. Django base64-encodes it for the token call |
| `MC_BASE_URL` | Optional. Default `https://cpaas.messagecentral.com` |
| `UB_OTP_PROVIDER` | Optional. Leave empty: it becomes `message_central` when both values above are set, otherwise `console` |

With both credentials empty, the `console` provider is used: the code is
printed in the Django log and nobody is texted. Tests and the automated browser
checks always use `console`.

Removed: `UB_FAST2SMS_API_KEY`, `UB_FAST2SMS_ALLOW_QUICK`. The Fast2SMS key has
been deleted from `backend/.env`.

The frontend needs nothing new. It already reads the API address from
`NEXT_PUBLIC_API_BASE_URL` in `frontend/.env.local`.

## 2. Run it locally and test with a real number

```bash
# 1. Credentials
cd ~/Projects/ims-platform
echo 'MC_CUSTOMER_ID=<your customer id>' >> backend/.env
echo 'MC_PASSWORD=<your password>'       >> backend/.env

# 2. Django on :8000 (creates the database if needed, migrates, serves)
scripts/dev-backend.sh
#    or, if you use Docker for the API (it reads backend/.env too):
#    docker compose -f docker-compose.backend.yml up --build

# 3. Next.js on :3000, in a second terminal
scripts/dev-frontend.sh
```

If Django was already running, restart it so it reads the new values. The
database change in this work (`platform` migration 0017) is already applied to
your local database; on any other database run
`cd backend && python manage.py migrate`.

Then:

1. Open http://localhost:3000/signup.
2. Enter your own 10-digit mobile number and tap **Send code**.
3. A 4-digit code arrives by SMS. Type it; the fourth digit submits.
4. A new number lands on business setup. A number that already has an account
   lands in its business.
5. To check resend: wait for the 60-second countdown, then tap **Resend code**.

If no SMS arrives, look at the Django log for a line starting
`message_central.` — it names their response code, for example
`message_central.token_refused` (wrong customer id or password) or
`message_central.send_refused code=…`. The screen shows "We couldn't send the
code right now" in that case instead of pretending it was sent.

To confirm which provider a running server is using:

```bash
cd backend && python manage.py shell -c \
  "from django.conf import settings; print(settings.UB_OTP_PROVIDER)"
```

## 3. Endpoints

The existing URLs are kept, so the frontend flow did not change shape.

| Call | Body | Answer |
| --- | --- | --- |
| `POST /api/v1/auth/otp/request` | `{ "mobile": "9876543210" }` | `{ challenge_id, expires_in, retry_after: 60 }` |
| `POST /api/v1/auth/otp/verify` | `{ "challenge_id": "…", "code": "1234" }` | The same session response and cookies as before; a new number is created as a user |

Errors the screen shows:

| Case | HTTP | Code |
| --- | --- | --- |
| Not an Indian mobile number | 400 | `validation_error` on `mobile` |
| Asked again inside 60 seconds, or too many requests | 429 | `otp_throttled` with `retry_after` |
| Wrong code | 400 | `otp_invalid`, `reason: incorrect`, `attempts_left` |
| Expired or already-used code | 400 | `otp_invalid`, `reason: expired` / `used` |
| Message Central refused or was unreachable | 502 | `provider_error` |

## 4. Where this differs from the brief, and why

- **`verificationId` stays in Django.** The brief had the browser hold it and
  send `{mobile, verificationId, code}`. The browser holds our `challenge_id`
  instead, and Django keeps Message Central's id against it. A pair supplied by
  the client could be used to replay one number's verification against another
  number.
- **`urllib`, not `requests`.** The project's rule (ADR-021) is no new
  packages, and `requests` is not installed. Behaviour is the same: 10-second
  timeouts, non-success responses logged.
- **URL names kept** as `/auth/otp/request` and `/auth/otp/verify` rather than
  `/send-otp/` and `/verify-otp/`, as the brief allowed.
- **A local `console` provider is kept** for runs without credentials, tests
  and browser checks. It is the only place a code is still generated by us.
- **Mobile validation** accepts the forms people type (`98765 43210`,
  `+91…`, a leading `0`) and normalises them to a number matching
  `^[6-9]\d{9}$`. Codes of 4 to 6 digits are accepted.
- **CORS/CSRF:** `http://localhost:3000` was already allowed locally.
