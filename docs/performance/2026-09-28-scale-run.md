# Scale run — 28 Sep 2026 (Sprint 12, Track H3)

Part 12 §12.5 sets the performance budgets and §12.8 asks for them to be met at 2,000
parties, 5,000 entries and 5,000 invoices, with the drift jobs clean on a seeded
100,000-row dataset. This run measured every list endpoint on such a book, read the plans
behind each one, fixed what the plans showed, and measured again.

## The book

`manage.py seed_scale --entries 100000 --parties 2000 --items 5000 --invoices 20000`
(39–48 s on the box; see `apps/reports/services/scale_seed.py`):

The seed writes by bulk insert but derives every cache the way the product does: movements
fold through `costing.apply_weighted_average` day by day, receipts allocate oldest-first, party
balances come from the ledger rows, document sequences move past the numbers used.

**Drift gates on it:** `check_invariants` — balances 2,000 checked, 0 drifted (240 ms);
stock 5,000 checked, 0 drifted (1.9 s). `recalc_balances --check` and `recalc_stock --check`
both exit 0.

## Method

`manage.py scale_probe --runs 20 --writes 20` issues each request the client makes,
in-process through DRF with an owner token, 20 times after one warm-up, and reports P50 / P95.
That is **server time** — routing, auth, permissions, queries, serialisation — without
network, TLS or a WSGI server in front. It then `EXPLAIN ANALYZE`s every SELECT the request
issued. On a one-tenant database a seq scan is usually the right plan (the tenant filter
matches every row), so each seq scan is re-planned with `enable_seqscan = off`: whatever
still seq-scans has no usable index ("NO INDEX"), and an index scan that discards more than
ten times what it keeps is reported as a weak index.

Box: 2 vCPU, 8 GB, PostgreSQL 16 local, other tracks running (load average 1.1–2.7 during the
runs); expect a quiet production host to be faster, not slower.

## What the plans showed, and the fixes

1. **Invoice list: every document read and top-N sorted for a page of 25.**
   `ix_sales_doc_kind_status (tenant, kind, status, -document_date)` cannot give one
   date order across the list's IN-lists on kind and status, so the planner scanned the
   tenant and sorted. Added `ix_sales_doc_tenant_date (tenant, -document_date,
   -created_at, -id)` — the list's own ordering, and the date range the registers, the
   GST summary and the day book read. `ix_purch_doc_tenant_date` is its purchases twin.
   Migrations `sales/0003_list_date_index`, `purchases/0002_list_date_index`.
2. **Payment list: all allocations joined and grouped before the LIMIT.** `allocated`
   was `Sum("allocations__amount")`; it is a correlated subquery now, evaluated for the
   rows on the page (`payments/selectors/payments.py`).
3. **Stock report JSON page: 5,000 rows built in Python to show 25** — the one budget that
   was failing (1.8 s). The page is sliced in SQL and the totals come from one outer
   aggregate (`reports/views/stock.py::page_and_totals`); the CSV keeps its generator. A
   test proves the page equals the file's rows and the totals equal its TOTAL row.
4. **No N+1 on any list.** Fifteen list endpoints were measured at 5 and 50 rows on a
   seeded book (`tests/performance/test_list_page_size_queries.py`); every one issues the
   same queries at both sizes. The ledger lists run one lookup per document source type on
   the page (LED-10's batched resolvers, by design — bounded by the number of document
   kinds, not the rows).

**Remaining seq scans are all full-period reads**, and with seq scans forbidden every one
has an index path ("NO INDEX" was empty for all 28 read probes): aging (all live entries of
the tenant), the totals aggregates on the item and invoice lists (over the filtered set,
which is the tenant), the FY registers and GST summary (half the seeded history), and the
dashboard recompute. The eleven "weak index" reports are all inside the GST summary's
anomaly checks — lines of the period filtered for an exempt code or a zero taxable value —
where reading every line of the period is what the check is.

Tests that pin this: `tests/performance/test_document_list_plans.py` (the three plans by
`EXPLAIN`, following `test_party_list_plans.py`), `test_list_page_size_queries.py`, and
`apps/reports/tests/test_aging_stock_reports.py::test_the_json_page_is_a_slice_of_the_file…`.

## Risks and next steps

- **O(history) reads.** Receivables aging (~0.5 s at 100,000 entries), ledger aging, the
  day book's opening cash and the dashboard recompute all read every entry of the tenant.
  Linear: a tenant at 500,000 entries would put receivables aging near 2.5 s. The fix, when
  it is needed, is a per-party aging snapshot or a dated running-total table; neither is
  MVP. The dashboard is already served from a snapshot (7 ms) and only `refresh=1` pays.
- **GST summary** is the heaviest request (34 queries, P95 0.8 s for a half-year). Folding
  its anomaly checks into fewer passes over the period's lines would roughly halve it.
- Numbers are in-process server time on a loaded 2-CPU box. The device budgets need the
  2 GB Android reference run (§12.8 "Performance and devices"), which this track does not do.
